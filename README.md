# 企业数据中心产品原型

本项目用于评审企业数据中心的核心流程：**FTP/FTPS 接入（字段映射与独立脚本加工）/ 离线文件本地上传（固定模板） → 信源排序与融合 → 全量 / 增量更新 → 企业库 → 下游服务（批量订阅推送 / 标准 API）**。

当前模型为 13 张表、259 个标准字段：保留《企业库数据字典-产品批注-20261103.xlsx》的原 257 字段，并按 2026-11-05 用户需求新增风险事件「发布日期」「发布机构」2 字段；其中 159 个业务字段可映射、100 个中心治理字段不可由厂商覆盖。旧 15 字段仅作为兼容的公开服务投影，新增风险字段不自动对外发布。上游数据厂商通过 FTP/FTPS 或离线文件本地上传提供企业数据。离线上传使用固定模板补充资质、企业规模和产业链节点。企业和 `DEMO` 开头的代码均为虚构演示数据；FTP/FTPS 为明确标注的模拟文件流程，尚未建立真实网络连接。上游 API 对接已移除，下游标准 API 服务保持可用。

公开演示：[GitHub Pages](https://limenglifei.github.io/enterprise-data-center-prototype/) · 完整源码：[GitHub 仓库](https://github.com/limenglifei/enterprise-data-center-prototype)。

产品文档：[V2.6 产品需求文档](docs/enterprise-data-center-prd-v2.6.docx)。

本项目提供两种运行方式：

| 运行方式 | 数据保存 | API 执行边界 |
| --- | --- | --- |
| GitHub Pages 公开演示 | 本机 IndexedDB，配置、企业、脚本、任务及调试调用记录刷新后保留；不同浏览器不共享，清理站点数据会删除本机工作空间 | 上游仅支持文件接入；下游 API 发布和调试在当前浏览器模拟，Pages 不实际承载公网 API |
| 完整后端部署 | 配置、更新记录、企业库、接口发布配置与调试记录写入服务端 D1；上传原件仍保存在上传者浏览器 IndexedDB | 保留原有两条企业 API 路由与按服务 ID 分发的动态 API 路由；需配置 `ENTERPRISE_API_KEY` 和部署访问控制 |

公开版保留 FTP/FTPS 字段映射、独立脚本、「信源排序」、FTP 全量 / 增量更新、离线文件本地上传及原件下载，以及下游批量订阅推送和标准 API 服务的配置、文档、发布、停用、调试与调用明细。FTP 传输和 Webhook 投递仅提供浏览器演示流程，两种部署方式均未实现真实服务端连接或后台调度。历史 API 信源与任务迁移为停用、隐藏配置入口；保留原来源标识、已入库值、原始记录、处理历史与血缘，不把旧厂商数据改称文件来源。

### 生成 GitHub Pages 公开版

```sh
node scripts/build-github-pages.mjs
```

输出目录为 `pages-dist/`，不需要安装项目依赖即可构建。将该目录内容发布至 GitHub Pages 的 `gh-pages` 分支根目录，并将 Pages 来源设为 `gh-pages`、`/`。目录包含 `.nojekyll`，支持仓库子路径访问；不要直接将需要 `/api/state` 的完整后端页面作为静态站点发布。

页面使用 `assets/<内容版本>/` 加载同一版本的样式、模块、示例数据和加工 Worker，避免浏览器混用旧脚本。发布时保留已上线的旧版本资产目录，使缓存中的旧页面仍可加载；GitHub Git Data API 发布应以前一棵发布树作为 `base_tree`，覆盖当前构建文件。工作空间仍按页面路径保存，资源版本变化不会清空浏览器数据。

下游服务和总览仅统计已发布的批量订阅与标准 API；旧工作空间中的其他服务配置不参与当前统计。

源码保存在 `main`，公开页面产物通过 GitHub Git Data API 发布至 `gh-pages`。发布目录中的 `PUBLISH_MANIFEST.json` 记录来源提交和文件哈希，便于核对源码与演示版本。

## 1. 功能范围

| 模块 | 当前可操作能力 |
| --- | --- |
| 数据总览 | 已移除右上角「查看数据存储」「运行更新」两个快捷按钮；查看企业量、来源记录、字段数和服务调用；进入各处理环节；查看最近更新结果。 |
| 数据接入 · FTP/FTPS 对接 | 默认企查查 FTP、启信宝 FTP、天眼查 FTP 三家独立来源；配置协议、主机端口、目录、规则、格式和用户名；先选择目标子表再选择字段，按模块筛选或搜索、增删映射行并绑定已发布脚本；预览远端演示文件、模拟接入并查看任务/记录，同一成功文件版本去重。 |
| 数据接入 · 离线文件本地上传 | 按 6 列固定模板上传 CSV / XLSX，校验后按统一社会信用代码关联更新；不提供文件字段映射，也不需要选择或发布加工脚本。记录信源名称、文件名称、下载链接、时间、行数与处理状态；原件保存在当前浏览器 IndexedDB。 |
| 信源排序 | 按模块及字段搜索，配置三家 FTP 与离线上传的第一、第二、第三、第四优先级；调整位置时交换重复来源，保存后重算，其他模块规则保留。活动来源优先，历史停用候选仅在无有效值时回退；历史来源不再提供新排序、手动选源或脚本绑定。 |
| 脚本管理 | 维护 FTP/FTPS 字段加工：新建脚本、保存草稿、用输入值测试、发布版本；已发布脚本可以新建版本，字段映射显式选择所需版本。 |
| 更新任务 | 「任务配置」「任务执行」双页签；仅选择 FTP/FTPS 来源，配置全量/增量、频率和北京时间执行点，任务独立维护检查点。离线上传不参与定时任务。 |
| 数据存储 | 查看统一企业库并按企业名称或代码检索；企业档案将 13 个模块纵向连续展示，目录锚点定位对应章节，多条明细各用独立记录卡；未采集模块保留完整字段名称与空态，中心字段折叠查看；对当前企业、当前明细、当前字段查看候选来源、手动切换或恢复自动，返回时保留原位置。 |
| 批量订阅推送 | 按行业/地区/荣誉资质配置条件、预览企业、发布/暂停、模拟全增量推送、失败重试及投递详情。 |
| API 封装与发布 | 提供企业批量筛选与单企业精准查询两类服务；点击「新增API服务」填写名称、服务 ID、服务类型、版本和描述，可新增多个同类型但不同 ID 的接口。新服务默认为草稿；支持配置、参数文档、发布、停用和在线调试，调试使用实际已入库结果并记录调用。 |

下游主菜单为「下游服务」，批量订阅推送位于首个页签，标准 API 服务位于第二个页签。原有 `POST /api/v1/enterprises/search` 和 `GET /api/v1/enterprises/query?keyword=...` 保留；新增 标准 API 服务使用 `/api/v1/services/{id}`，根据 `kind` 确定方法：`search` 为 POST 批量筛选，`query` 为 GET 精准查询。服务共用统一企业库，同类型可配置多个不同 ID 的接口。完整源码包含服务端路由、Bearer 鉴权、发布状态控制、参数校验与标准响应；GitHub Pages 仅演示服务配置和浏览器内调试，不实际承载公网 API。限流、租户级调用授权、API 网关和计费仍属于后续建设范围。

## 2. 推荐演示路径

1. 打开「数据总览」，查看已初始化的演示来源、企业数据和处理任务；这些数字来自实际原型状态。
2. 进入「数据接入 → FTP/FTPS 对接」，检查连接、目录、文件规则、格式与用户名；界面明确标注模拟连接。
3. 打开「字段映射」，先选择目标子表，再选择该表字段；下拉展示中文名称、完整 `table.field` 标识及数据类型。按模块或搜索定位、增删映射行并选择已发布脚本；预览远端演示文件并模拟接入。
4. 进入「脚本管理」，测试日期、金额或多值拆分逻辑，发布新版本后回到 FTP 映射显式切换绑定。
5. 在「信源排序」按模块或字段搜索，调整四级来源顺序并保存；进入企业档案，向下查看连续的 13 节或点击目录锚点定位模块。在各独立记录卡的字段旁点击「来源」，核对当前明细序号、自然键和候选值，可手动选择可用来源或恢复自动；返回后保留所在记录、滚动位置和中心字段展开状态。
6. 进入「更新任务 → 任务配置」，新增 FTP/FTPS 全量或增量任务，选择频率和执行时间；运行后在「任务执行」查看文件和处理明细。重复运行确认不重复新增。
7. 在「数据接入 → 离线文件本地上传」下载 CSV 模板，按企业全称、统一社会信用代码、企业资质、企业规模、产业链节点、数据更新时间 6 列填写、预览并导入；无须配置映射或脚本。检查上传记录并下载原件。
8. 进入「API 封装与发布」，查看已有接口的方法、路径及参数文档；点击「新增API服务」，填写名称、唯一服务 ID、类型（`search` / `query`）、版本和描述，保存为草稿。可新增多个同类型接口；发布后用在线调试运行组合筛选或信用代码 / 全称精准查询，核对新路径 `/api/v1/services/{id}`。输入局部名称应返回 404；停用接口后调试应返回 403。
9. 刷新页面，确认上述配置、任务、上传记录、企业变化、接口状态及调试记录仍然存在。本机文件原件仅在同一浏览器可下载。

采购字段目录表用于定义数据结构，不能作为企业明细导入。离线文件本地上传数据须为“一行一家企业”，首行为固定模板的 6 个字段名。

## 3. 标准字段与融合规则

标准字段定义位于 `public/prototype/enterprise-dictionary.mjs`，`core.mjs` 的 `FIELD_DEFS` 引用同一份 V2.6 的 259 字段目录。13 张表包含 159 个可映射业务字段与 100 个中心治理字段；治理字段可查看，不参加厂商映射或手动选源。原工作簿及原 257 字段的元数据、顺序、来源行号保持不变；新增 2 字段以 `origin="本轮需求 V2.6"`、`requirementDate="2026-11-05"` 标明需求依据，`sourceRow`、`dictionaryRow` 均为 `null`，不作为原字典行。

| 标准子表 | 模块 | 关系 | 字段数 |
| --- | --- | --- | --- |
| `enterprise` | 工商基本信息 | 1:1 | 30 |
| `enterprise_contact` | 企业联系方式 | 1:N | 6 |
| `enterprise_address` | 地址与区位 | 1:N | 25 |
| `enterprise_industry` | 行业分类 | 1:N | 23 |
| `enterprise_annual_operation` | 年度经营与财务 | 1:N | 23 |
| `enterprise_listing` | 上市信息 | 1:N | 19 |
| `enterprise_shareholder` | 股东与股权 | 1:N | 25 |
| `enterprise_qualification` | 荣誉与资质 | 1:N | 23 |
| `enterprise_patent` | 专利明细 | 1:N | 18 |
| `enterprise_intellectual_property_summary` | 知识产权汇总 | 1:N | 13 |
| `enterprise_risk_event` | 风险事件明细 | 1:N | 16 |
| `enterprise_risk_summary` | 风险汇总 | 1:N | 19 |
| `enterprise_tag` | 企业标签（候选范围） | 1:N | 19 |

字段使用唯一的 `table.field` 标识。源字典行业四级中的重复 `industry_code`、`industry_name` 分别规范为 `industry_code_l1` 至 `industry_code_l4`、`industry_name_l1` 至 `industry_name_l4`；定义保留 `originalKey`、源表行号及规范说明，可回溯源字典，并非新增行业层级或合并原始字段。

风险事件明细本轮新增以下可映射业务字段，均可为空、默认 `null`：

| 标准字段 | 中文名称 | SQL 类型及格式 | 默认 FTP 来源路径 |
| --- | --- | --- | --- |
| `enterprise_risk_event.published_date` | 发布日期 | `date`，`YYYY-MM-DD`，校验实际日历日期 | `risk_events[].published_date` |
| `enterprise_risk_event.publishing_authority` | 发布机构 | `varchar(200)`，最多 200 个字符 | `risk_events[].publishing_authority` |

两字段按同一风险事件的候选来源参与排序、血缘和行级人工选源。来源未提供时保留未知，不用采集时间或推测机构填充。风险自然键继续使用 `risk_type` 和 `event_title`，更新发布日期或发布机构不改变既有 `rowKey` / `rowId`。旧状态升级仅为现有风险行补充空字段与空血缘，不改写原始证据；未修改的 V2.5 默认 FTP 映射补入 2 条新映射，自定义映射保留用户配置，重复升级不追加重复项。演示文件为首家虚构企业提供两条独立风险事件，日期和发布机构均明确标注为演示数据。

企业档案将上述 13 个模块纵向连续平铺，目录通过锚点定位章节，所有章节同时保留。1:N 数据按自然键保留独立记录卡，业务字段的名称、取值和「来源」入口在卡内纵向展示；联系方式、年度经营、股东、专利等不会压成单值或归入「专题补充」。中心生成 / 关联字段在各记录卡内折叠查看。没有采集到数据的模块也保留完整字段名称，并显示明确空态；空模块不生成明细记录或候选来源。查看字段来源后返回企业档案时恢复原企业、模块、记录、滚动位置、焦点及中心字段展开状态。

以下 15 个旧字段由 `LEGACY_FIELD_DEFS` 保留，用于既有筛选、精准查询和订阅的兼容公开投影；表中的旧分组不再代表当前企业档案导航。当前对外 API 仍只发布这组投影，新增模块字段不会自动扩展服务响应。


| 标准字段 key | 展示名称 | 类型 | 分组 |
| --- | --- | --- | --- |
| `enterpriseName` | 企业全称 | string，必填 | 工商信息 |
| `creditCode` | 统一社会信用代码 | string，必填 | 工商信息 |
| `legalPerson` | 法定代表人 | string | 工商信息 |
| `registrationStatus` | 经营状态 | string | 工商信息 |
| `establishedAt` | 成立日期 | date | 工商信息 |
| `registeredCapitalWan` | 注册资本（万元） | number | 工商信息 |
| `regionProvince` | 省份 | string | 工商信息 |
| `regionCity` | 城市 | string | 工商信息 |
| `regionDistrict` | 区县 | string | 工商信息 |
| `industry` | 行业 | string | 工商信息 |
| `businessScope` | 经营范围 | string | 工商信息 |
| `registeredAddress` | 注册地址 | string | 工商信息 |
| `qualifications` | 企业资质 | array | 专题补充 |
| `scale` | 企业规模 | string | 专题补充 |
| `chainNodes` | 产业链节点 | array | 专题补充 |

- 用标准化后的企业代码关联来源记录，同一企业生成稳定的内部企业 ID。
- FTP/FTPS 字段映射先选子表、再选标准字段；切换子表会清空旧字段，校验重复目标、必填项及不可覆盖的治理字段。映射行可增删，支持模块筛选和搜索；来源字段支持点路径与 `contacts[].contact_phone` 等集合路径。加工代码在「脚本管理」独立维护；本地文件保持固定模板，不提供字段映射或脚本绑定配置。
- 每个来源的同一家企业保留当前来源记录；较旧版本不覆盖较新版本。相同批次重复记录按来源时间处理。
- 每个标准字段按已配置的来源顺序选择首个非空候选。高优先级来源为空时回退下一来源；未选中的值保留为候选，可以追溯。
- 保存「信源排序」立即重新融合已有候选；单企业已手动指定来源的字段优先遵循手动选择，恢复自动后重新跟随排序。修改 FTP/FTPS 字段映射或脚本绑定用于下一次接入，需要重跑全量更新才能重新加工已保存的来源记录。
- 「数据存储 → 企业档案 → 模块明细 → 字段来源」使用 `rowId` 定位当前企业、当前明细、当前字段；弹窗展示明细序号与申请号、财年、股东名等自然键。可手动切换非空有效候选来源或恢复自动，选择持久化且不改变全局排序、其他明细或来源原始数据。手动指定跟随该来源后续最新有效值，来源为空或不可用时自动回退并保留选择意图；血缘展示手动来源及回退原因。保存后更新当前企业档案的有效取值；下游仍遵循既有公开投影，信用代码不可切换到其他主体。
- 新工作空间默认四级顺序为企查查 FTP、启信宝 FTP、天眼查 FTP、离线文件本地上传，可按标准字段调整。历史 API 仅保留候选回退，既有手动指定保留且可恢复自动，不能新增历史 API 选择。迁移保留既有记录与配置；后续更新或保存排序按当前自动顺序融合。
- 标准注册资本字段按字典使用元，FTP 的万元样例通过「万元 → 元」脚本转换；旧公开投影 `registeredCapitalWan` 继续使用万元。历史映射保留原字段、单位及加工规则，不能仅替换目标名称改变金额含义。带明确元、万、亿单位时按显式单位转换；无单位数值采用所绑定脚本的单位约定。未知币种或不明确格式报错，不自动换汇；真实厂商单位需结合已采购文档确认后选择脚本。

脚本通过浏览器 Worker 执行同步转换，主线程设有 2 秒超时。草稿不能绑定映射，发布新版本不会自动替换旧绑定。该执行方式用于原型加工验证，生产环境仍需独立的受控脚本执行服务。

## 4. 文件接入与下游接口

「数据接入」仅提供「FTP/FTPS 对接」「离线文件本地上传」两个页签。FTP/FTPS 支持连接配置、字段映射、远端演示文件及接入记录；离线文件使用固定模板。更新任务只接受 FTP/FTPS 信源，不再配置全部企业、条件筛选或上传名单等上游 API 专用范围。

历史 API 信源和任务保留历史身份与处理记录，但被停用且不显示在可用配置候选中。旧任务不得手动运行、启用或自动调度；批处理与任务执行层分别校验来源，`/api/vendor` 的 GET/POST 均返回 `410 UPSTREAM_API_REMOVED`，不读取凭证、不请求厂商。现有下游查询继续读取已入库的企业库。

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| `/api/state` | GET / PUT | 读取或按 revision 保存共享原型状态，冲突返回 409。 |
| `/api/vendor` | GET / POST | 已移除的上游接入边界，固定返回 410。 |
| `/api/v1/enterprises/search` | POST | Bearer 鉴权；组合条件筛选已入库企业并分页返回。 |
| `/api/v1/enterprises/query?keyword=...` | GET | Bearer 鉴权；信用代码或全称完全匹配。 |
| `/api/v1/services/{id}` | POST / GET | 已发布标准 API 服务按 ID 分发；search 为 POST，query 为 GET。 |

### 对外 API 部署与鉴权

完整后端部署需在 Worker Secrets / 服务端绑定中设置 `ENTERPRISE_API_KEY`，调用方携带 `Authorization: Bearer <API_KEY>`。未配置密钥返回 503，缺失或错误密钥返回 401；接口草稿 / 停用返回 403，精准查询未匹配返回 404。接口配置保存后变为草稿，需在控制台发布后才开放调用。页面不展示或保存真实密钥。

控制台通过「新增API服务」保存 `name`、`id`、`kind`、`version`、`description`。服务 ID 按唯一 URL slug 校验，不能与已有服务重复；同一种 `kind` 可创建多个不同 ID 的接口。新服务默认草稿，其动态路径为 `/api/v1/services/{id}`。动态路由支持 GET / POST 分发，实际允许的方法由服务类型决定；`search` 使用 POST，`query` 使用 GET。原有两条 `/api/v1/enterprises/*` 路径继续保留，服务目录中的新旧接口均支持发布、停用、文档和调试。

批量接口请求体为 JSON 对象，支持 `regionProvince`、`regionCity`、`regionDistrict`、`industry`、`qualifications`、`scale`、`chainNodes`、`keyword`，以及整数 `page`（默认 1）、`pageSize`（默认 20，最大 100）；字符串最长 200 字符，请求体最大 16 KB。不支持的参数会报错。精准接口仅接收一个 `keyword` 查询参数，不做模糊检索。

两类服务统一返回 `{ requestId, code, message, data }`。批量结果 `data` 包含 `count`、`page`、`pageSize`、`records`；精准结果包含 `count`、`record`。企业结果只包含中心 ID、15 个兼容公开字段及数据更新时间，不暴露原始来源载荷、内部血缘或配置。接口仅查询已入库数据，不触发厂商付费查询。控制台在线调试复用同一套筛选和参数校验逻辑，持久化最近 100 条浏览器调试记录；API 列表的「最近调用次数」按已保留记录统计近 24 小时成功及失败的已执行调用，点击次数打开该接口明细，可切换近 24 小时与全部保留记录。明细包含时间、调用时服务名与版本、请求 ID、状态码、业务码、返回企业数和执行方式，独立的「最近调试调用」模块已移除。真实外部请求不会覆盖共享状态，也不计入本原型调用统计，生产请求审计需另接服务端日志系统。

### 下游服务新增方式

导航为「下游服务」，按顺序包含「批量订阅推送」「标准 API 服务」两个页签，首次进入和刷新默认选中批量订阅推送；既有 API 接口和调用明细继续可用。

- **FTP 接入**：只保存演示配置，不接收密码；文件列表为明确标注的虚构远端目录，不发送网络请求。支持 JSON / UTF-8 CSV 结构的样例预览、字段映射及已发布脚本转换；使用同一批处理引擎写入来源候选、企业库和任务，参与信源排序。全量不按缺失行删除，增量采用来源时间及成功检查点；修复失败映射后可重试。更新配置统一在更新任务中维护，正式轮询需后续服务端执行。
- **批量订阅推送**：按国民经济行业、注册地区、荣誉资质配置条件，支持预览匹配、发布/暂停、全量或增量、Webhook 地址及频率、模拟投递和明细。一个维度的多值取 OR，维度间取 AND；未选条件表示不限。行业使用当前演示库已有文本，不将样例行业包装成官方完整行业编码字典。增量以成功模拟投递的快照识别变化，失败不推进基线，可重试；首次建立全量基线。Webhook 为 HTTPS 配置，当前流程不发送真实网络请求，定时和真实重试需服务端实现。

## 5. 全量与增量更新语义

**全量更新**处理 FTP/FTPS 目录内符合规则的文件并合并来源记录；缺失行不会删除已有企业。离线文件本地上传也按固定模板合并写入。

**增量更新**按当前任务独立的成功检查点发现文件，并按来源更新时间处理新增与变化；时间窗口为 `(windowStart, windowEnd]`，排除起点、包含终点。每个任务的进度互不影响。

来源时间缺失时会标记为推定采集时间，不将其当作可信的厂商变更时间；推定时间记录不会覆盖已有明确来源时间的记录。成功检查点只在本批无失败时推进，且不倒退。任务同时保存来源新增 / 更新 / 未变数量、中心企业新增 / 变化数量和失败原因，避免把来源变化误认为企业总量增长。

更新策略统一在「更新任务 → 任务配置」管理，「任务执行」展示历史并支持运行任务，手动完成后自动切换到执行页签。仅支持 FTP/FTPS，支持新增、编辑、启用、暂停和立即运行；每日/每周使用北京时间，每周另选执行日；按小时从上次完成时刻推进。离线文件本地上传由用户手动接入，不参与定时拉取。

原信源策略只迁移一次到 `state.updateJobs`，保留配置与检查点。任务定义与 `state.tasks` 运行日志分开；同一来源可创建多个任务，各自维护检查点。更换来源或全增量方式会重置该任务基线，修改名称和执行频率保留基线。完整成功才推进检查点，部分失败不推进；空批不会将检查点推进到执行时间。连接/校验前置失败也保留记录并计算下一次执行，避免无记录反复执行。

原型每 30 秒检查一次到期的演示 FTP/FTPS 任务，仅页面打开时运行。FTP 任务按自身检查点读取演示文件，完整成功才登记文件版本；不受其他任务去重记录阻挡。关闭页面后不运行；生产需要独立的服务端调度和传输。

## 6. 文件导入

支持 UTF-8 CSV 和常见 `.xlsx` 文件的首个工作表；单文件不超过 20 MB、最多 5 万行，仍受整份原型状态 50 MB 上限限制。按模板填充数据，表头不得缺失或重复，文件先检查预览，再确认入库。

离线文件本地上传使用 6 列固定模板：企业全称、统一社会信用代码、企业资质、企业规模、产业链节点、数据更新时间。企业全称与统一社会信用代码必填，其余列的值可空；系统按统一社会信用代码关联并更新企业来源记录。资质和产业链节点支持中文 / 英文分号、逗号拆分并去重。此流程不提供文件字段映射，也不需要选择、测试或发布加工脚本；请直接按模板填写，不使用自定义列名。浏览器不支持当前 XLSX 解压方式时，可另存为 UTF-8 CSV。

「离线文件本地上传」页签展示每次上传记录，包含信源名称、文件名 / 下载链接、上传时间、行数与处理结果。原件以 Blob 保存在当前浏览器的 IndexedDB，下载时生成临时文件链接；不是服务端永久 URL。完整后端部署只共享记录元数据，不上传原件到 D1，因此另一浏览器 / 设备可能看得到记录但无法下载原件。清除浏览器站点数据会删除本机原件；原型未实现集中对象存储。

## 7. 完整后端的持久化与原型边界

- 数据存储：D1 的 `prototype_state` 表中保存一份共享工作空间状态，包含来源配置、映射、脚本、来源记录、企业库、任务与服务调用。
- 并发保存：客户端携带 `baseRevision`，服务端原子比较并递增 revision；冲突返回最新状态，避免静默覆盖其他窗口的保存。
- 可恢复性：普通刷新会重新从服务端加载；不会用浏览器临时状态替代服务端保存成功。共享存储不可用时展示明确错误。
- 容量：单份状态 JSON 不超过 50 MB。当前采用整体快照保存，适合原型评审；规模化使用需要拆分实体表、分页、任务队列和历史版本存储。
- 工作空间：当前所有有权访问本原型的用户共享同一份演示状态，尚未实现应用内多租户、细粒度角色权限或独立数据集。
- 部署访问控制：下游企业 API 与动态服务路由使用 `ENTERPRISE_API_KEY` Bearer 鉴权；完整后端的控制台和状态管理路由仍需部署访问边界。GitHub Pages 不部署服务端路由。
- 查询：企业筛选和单企精准查询使用已入库数据；精准查询不会在后台自动发起新的厂商付费查询。未找到时需要先通过接入任务补齐企业。
- 历史：保留当前来源候选、处理任务、上传记录及浏览器调试记录，不是完整的历史快照仓库；本版本不实现删除同步、集中上传原件存储或后台无人值守调度。

## 8. 本地运行、检查与构建

### 环境与安装

需要 Node.js `>=22.13.0`，支持 Windows、macOS、Linux。首次在独立源码目录安装依赖：

```sh
npm run install:ci
```

该命令按锁文件执行安装；已有正常依赖时无需反复安装，不要同时启动多个安装进程。

### 初始化 D1 并预览

在项目根目录执行：

```sh
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_sparkling_harrier.sql
npm run dev -- --hostname 127.0.0.1 --port 4317
```

打开服务器实际输出的地址，并访问 `/prototype/index.html`。本例使用 `http://127.0.0.1:4317/prototype/index.html`；不指定端口时 portable 开发模式默认从 5173 启动。迁移只需对新的本地数据库执行一次；已有 `prototype_state` 表时不要重复执行建表 SQL。

开发和构建预览共享 `.wrangler/state` 下的本地 D1 状态。缺少 DB 绑定或未迁移时，界面会显示共享存储 / 数据表未就绪信息。

### 功能检查与构建预览

```sh
node --test tests/*.test.mjs
# 单独检查本轮字典领域与界面契约
node --test tests/enterprise-dictionary.test.mjs tests/risk-event-v26.test.mjs tests/dictionary-ui.test.mjs tests/enterprise-detail-ui.test.mjs
npm run build
npm start -- --port 4318
```

`npm start` 使用构建生成的 Worker 配置在本地预览，不会执行发布。以服务器实际输出的 URL 为准。

项目保留 Vinext、Cloudflare Worker、D1 和 Drizzle 基础结构；修改数据库结构后可运行 `npm run db:generate` 生成迁移。无需另建 `wrangler.jsonc`。
