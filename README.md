# 企业数据中心产品原型

本项目用于评审企业数据中心的核心流程：**API / FTP 接入（字段映射与独立脚本加工）/ 固定模板文件上传 → 信源排序与融合 → 全量 / 增量更新 → 企业库 → 下游服务（API / 动态 SQL / 批量订阅推送）**。

首期保留 15 个标准字段，提供企查查、天眼查、启信宝信源模板，并支持新增第三方厂商或自定义业务系统。表格文件补充资质、企业规模和产业链节点。界面中的企业、以 `DEMO` 开头的代码和接口快照均为虚构演示数据；本项目没有取得或验证任何厂商付费接口授权，也不表示已经真实接通厂商。启信宝及自定义系统采用产品标准字段演示结构，不代表其官方 API 文档。

公开演示：[GitHub Pages](https://limenglifei.github.io/enterprise-data-center-prototype/) · 完整源码：[GitHub 仓库](https://github.com/limenglifei/enterprise-data-center-prototype)。

本项目提供两种运行方式：

| 运行方式 | 数据保存 | API 执行边界 |
| --- | --- | --- |
| GitHub Pages 公开演示 | 本机 IndexedDB，配置、企业、脚本、任务及调试调用记录刷新后保留；不同浏览器不共享，清理站点数据会删除本机工作空间 | 厂商真实请求明确拒绝；下游 API 发布和调试在当前浏览器模拟，Pages 不实际承载公网 API |
| 完整后端部署 | 配置、更新记录、企业库、接口发布配置与调试记录写入服务端 D1；上传原件仍保存在上传者浏览器 IndexedDB | 包含固定厂商代理、原有两条企业 API 路由与按服务 ID 分发的动态 API 路由；需配置厂商凭证、`ENTERPRISE_API_KEY` 和部署访问控制 |

公开版保留信源请求 / 返回参数配置、API / FTP 字段映射、独立脚本、「信源排序」菜单、全量 / 增量更新、固定模板 CSV / XLSX 上传及记录下载、API 新增 / 封装 / 文档 / 发布 / 停用 / 调试的完整交互，并增加 FTP 文件模拟接入、动态 SQL 和批量订阅推送。FTP 传输、SQL 执行和 Webhook 投递目前仅提供浏览器演示流程；两种部署方式均未实现它们的真实服务端连接、自动调度或外部投递。请使用演示数据评审。后文 D1、`/api/vendor`、`/api/v1/enterprises/*` 和 `/api/v1/services/{id}` 配置说明适用于完整后端运行方式。

### 生成 GitHub Pages 公开版

```sh
node scripts/build-github-pages.mjs
```

输出目录为 `pages-dist/`，不需要安装项目依赖即可构建。将该目录内容发布至 GitHub Pages 的 `gh-pages` 分支根目录，并将 Pages 来源设为 `gh-pages`、`/`。目录包含 `.nojekyll`，支持仓库子路径访问；不要直接将需要 `/api/state` 的完整后端页面作为静态站点发布。

页面使用 `assets/<内容版本>/` 加载同一版本的样式、模块、示例数据和加工 Worker，避免浏览器混用旧脚本。发布时保留已上线的旧版本资产目录，使缓存中的旧页面仍可加载；GitHub Git Data API 发布应以前一棵发布树作为 `base_tree`，覆盖当前构建文件。工作空间仍按页面路径保存，资源版本变化不会清空浏览器数据。

源码保存在 `main`，公开页面产物通过 GitHub Git Data API 发布至 `gh-pages`。发布目录中的 `PUBLISH_MANIFEST.json` 记录来源提交和文件哈希，便于核对源码与演示版本。

## 1. 功能范围

| 模块 | 当前可操作能力 |
| --- | --- |
| 数据总览 | 已移除右上角「查看数据存储」「运行更新」两个快捷按钮；查看企业量、来源记录、字段数和服务调用；进入各处理环节；查看最近更新结果。 |
| 数据接入 · API 对接 | 展示企查查、天眼查、启信宝及已新增厂商 / 系统；配置方法、地址、请求 Query / Header / Body、返回记录根路径及返回字段；测试解析；配置字段映射和脚本绑定，更新策略集中在更新任务维护。已移除单独维护的纳管企业清单。 |
| 数据接入 · FTP 对接 | 配置 FTP / FTPS、主机端口、目录、规则、格式和用户名；独立维护映射及脚本绑定；预览远端演示文件、模拟接入并查看任务/记录，同一成功文件版本去重。 |
| 数据接入 · 本地文件上传 | 按 6 列固定模板上传 CSV / XLSX，校验后按统一社会信用代码关联更新；不提供文件字段映射，也不需要选择或发布加工脚本。记录信源名称、文件名称、下载链接、时间、行数与处理状态；原件保存在当前浏览器 IndexedDB。 |
| 信源排序 | 独立菜单，按标准字段配置所有信源顺序，保存后立即重新融合并可追溯候选来源。 |
| 脚本管理 | 维护 API / FTP 字段加工：新建脚本、保存草稿、用输入值测试、发布版本；已发布脚本可以新建版本，字段映射显式选择所需版本。 |
| 更新任务 | 按「任务配置」「任务执行」双页签展示；新增/编辑任务，选择 API/FTP 来源、全量或增量、手动/按小时/每日/每周、北京时间执行点；启停、立即运行、查看任务记录和独立检查点。 |
| 数据存储 | 查看统一企业库；按企业名称或代码检索；查看工商档案、专题数据及字段候选来源；对单企业单字段手动切换来源或恢复自动。 |

| 动态 SQL 查询 | 保存参数化只读查询模板、发布/停用、绑定参数执行，查看结果及执行记录。 |
| 批量订阅推送 | 按行业/地区/荣誉资质配置条件、预览企业、发布/暂停、模拟全增量推送、失败重试及投递详情。 |

下游主菜单为「下游服务」，API 目录位于首个页签。原有 `POST /api/v1/enterprises/search` 和 `GET /api/v1/enterprises/query?keyword=...` 保留；新增 标准 API 服务使用 `/api/v1/services/{id}`，根据 `kind` 确定方法：`search` 为 POST 批量筛选，`query` 为 GET 精准查询。服务共用统一企业库，同类型可配置多个不同 ID 的接口。完整源码包含服务端路由、Bearer 鉴权、发布状态控制、参数校验与标准响应；GitHub Pages 仅演示服务配置和浏览器内调试，不实际承载公网 API。限流、租户级调用授权、API 网关和计费仍属于后续建设范围。

## 2. 推荐演示路径

1. 打开「数据总览」，查看已初始化的演示来源、企业数据和处理任务；这些数字来自实际原型状态。
2. 进入「数据接入 → API 对接 → 企查查 → 接口及参数配置」，保持「演示 API」模式；检查请求入参、返回根路径和返回参数，保存并测试响应。也可新增 API 对接，选择厂商模板或自定义系统。
3. 在所选 API 信源的「字段映射」中查看来源字段与标准字段的对应关系，例如 `Name → 企业全称`、`RegistCapi → 注册资本（万元）`。点击「转换预览」检查实际转换结果，再保存映射。
4. 进入「脚本管理」，测试 API 加工所需的金额、日期或多值拆分脚本；如需修改已发布脚本，创建并发布新版本，再回到 API 字段映射切换绑定。
5. 在「信源排序」中调整某个字段的来源顺序，保存并重新融合；进入企业档案，点击该字段的「来源」检查当前取值与保留候选。
6. 打开「运行更新」，选择全量更新，先执行变更快照 V2，再重复执行同一快照，核对第一次新增 / 变化与第二次未变化的实际结果。也可以选择初始快照 V1，检查旧版本不会覆盖较新来源记录。
7. 在「数据接入 → 本地文件上传」下载 CSV 模板，保留企业全称、统一社会信用代码、企业资质、企业规模、产业链节点、数据更新时间这 6 列，每行填写一家企业；企业全称、统一社会信用代码必填，其余值可空。保持企业代码与工商记录一致，填写信源名称、预览并上传入库，无需配置文件字段映射或加工脚本；核对上传记录，再通过文件链接下载原件。进入企业库核对专题字段。
8. 进入「API 封装与发布」，查看已有接口的方法、路径及参数文档；点击「新增API服务」，填写名称、唯一服务 ID、类型（`search` / `query`）、版本和描述，保存为草稿。可新增多个同类型接口；发布后用在线调试运行组合筛选或信用代码 / 全称精准查询，核对新路径 `/api/v1/services/{id}`。输入局部名称应返回 404；停用接口后调试应返回 403。
9. 刷新页面，确认上述配置、任务、上传记录、企业变化、接口状态及调试记录仍然存在。本机文件原件仅在同一浏览器可下载。

采购字段目录表用于定义数据结构，不能作为企业明细导入。本地上传数据须为“一行一家企业”，首行为固定模板的 6 个字段名。

## 3. 标准字段与融合规则

原 PRD 字段范围在本原型中收敛为以下 15 个核心字段，定义位于 `public/prototype/core.mjs` 的 `FIELD_DEFS`。

| 标准字段 key | 展示名称 | 类型 | 分组 |
| --- | --- | --- | --- |
| `enterpriseName` | 企业全称 | string，必填 | 工商信息 |
| `creditCode` | 统一社会信用代码 | string，必填 | 工商信息 |
| `legalPerson` | 法定代表人 | string | 工商信息 |
| `registrationStatus` | 经营状态 | string | 工商信息 |
| `establishedAt` | 成立日期 | date | 工商信息 |
| `registeredCapitalWan` | 注册资本（万元） | number | 工商信息 |
| `regionProvince` | 省份 | string | 工商信息 |
| `regionCity` | 城市 | string | 工商信息 |
| `regionDistrict` | 区县 | string | 工商信息 |
| `industry` | 行业 | string | 工商信息 |
| `businessScope` | 经营范围 | string | 工商信息 |
| `registeredAddress` | 注册地址 | string | 工商信息 |
| `qualifications` | 企业资质 | array | 专题补充 |
| `scale` | 企业规模 | string | 专题补充 |
| `chainNodes` | 产业链节点 | array | 专题补充 |

- 用标准化后的企业代码关联来源记录，同一企业生成稳定的内部企业 ID。
- API 字段映射只描述来源字段、标准字段和脚本版本的绑定；加工代码在「脚本管理」独立维护。API 来源字段支持点路径。本地文件使用固定模板，不提供字段映射或脚本绑定配置。
- 每个来源的同一家企业保留当前来源记录；较旧版本不覆盖较新版本。相同批次重复记录按来源时间处理。
- 每个标准字段按已配置的来源顺序选择首个非空候选。高优先级来源为空时回退下一来源；未选中的值保留为候选，可以追溯。
- 保存「信源排序」立即重新融合已有候选；单企业已手动指定来源的字段优先遵循手动选择，恢复自动后重新跟随排序。修改 API / FTP 字段映射或脚本绑定用于下一次接入，需要重跑全量更新才能重新加工已保存的来源记录。
- 「数据存储 → 工商详情 → 字段来源」支持对当前企业的当前字段手动切换非空有效候选来源，或恢复自动取值；选择持久化且不改变全局排序、其他企业、原始来源数据。手动指定跟随该来源后续最新有效值，来源为空或不可用时自动回退并保留选择意图；血缘展示手动来源及回退原因。融合结果立即供 API / SQL / 订阅读取，信用代码不可切换到其他主体。
- 工商字段默认优先企查查、其次天眼查、本地文件；专题字段默认优先文件、其次企查查、天眼查，均可按字段调整。
- 金额脚本统一输出人民币万元。带明确元、万、亿单位时按显式单位转换；无单位数值采用所绑定脚本的单位约定。未知币种或不明确格式报错，不自动换汇。真实厂商单位需结合已采购文档确认后选择脚本。

脚本通过浏览器 Worker 执行同步转换，主线程设有 2 秒超时。草稿不能绑定映射，发布新版本不会自动替换旧绑定。该执行方式用于原型加工验证，生产环境仍需独立的受控脚本执行服务。

## 4. API 接入与真实模式配置

### 信源与参数配置

「数据接入」按顺序提供「API 对接」「FTP 对接」「本地文件上传」三个页签。API 对接支持新增厂商或业务系统，分别配置请求方法、接口地址、Query / Header / Body 入参、返回记录根路径和返回字段声明。入参支持 `{{keyword}}`、`{{creditCode}}`、`{{enterpriseName}}`、`{{updatedAfter}}`、`{{page}}`、`{{pageSize}}` 上下文占位符。返回字段加工仍由字段映射绑定独立脚本完成。启信宝与自定义系统可以使用演示 JSON 验证整条链路；真实接入须补充授权文档及对应服务端适配器。

逐企接口直接从当前企业库取信用代码 / 全称作为请求上下文；列表或系统接口可按配置执行单次请求。本版本没有单独维护的纳管企业清单，也没有自动遍历第三方分页直到全国全量的能力。

### 已实现的真实厂商代理模板

下表描述当前代码采用的固定接口模板；具体返回字段、权限与单位以采购账号的正式 API 文档为准。

| 厂商 | providerId | 当前模板 | 服务端凭证 |
| --- | --- | --- | --- |
| 企查查 | `qcc` | `GET https://api.qichacha.com/ECIV4/GetBasicDetailsByName?keyword=...` | `QCC_APP_KEY`、`QCC_SECRET_KEY` |
| 天眼查 | `tyc` | `GET https://open.api.tianyancha.com/services/v4/open/baseinfoV3?keyword=...` | `TYC_TOKEN` |

企查查代理按代码模板生成 `Timespan` 和 `Token` 签名；天眼查代理设置 `Authorization` 请求头。浏览器通过本项目 `/api/vendor` 请求服务端代理，页面不接收或保存真实密钥。

参考入口：[企查查 API 文档](https://openapi.qcc.com/dataApi/410)、[天眼查 API 文档](https://open.tianyancha.com/open/365)。

本机开发可在启动服务器前设置进程环境变量，例如 PowerShell：

```powershell
$env:QCC_APP_KEY = '<已授权的 AppKey>'
$env:QCC_SECRET_KEY = '<已授权的 SecretKey>'
$env:TYC_TOKEN = '<已授权的 Token>'
npm run dev -- --hostname 127.0.0.1 --port 4317
```

只接入一家厂商时配置对应变量即可。托管环境使用平台的服务端 Secrets / Worker bindings。凭证不能写入源码、前端脚本、导入文件或提交到版本库。

在「接口及参数配置」切换真实模式后，设置入参及返回结构，保存后再测试 / 执行。测试默认使用统一企业库示例作为上下文，可在请求入参中配置固定值。连接测试仅展示响应；运行接入任务才会执行映射加工并入库。缺少凭证时服务端返回 `412 CREDENTIALS_NOT_CONFIGURED`，不会回退为虚构的真实成功。启信宝 / 自定义系统尚未实现真实代理时返回 `501 ADAPTER_NOT_IMPLEMENTED`，不发送网络请求。

### 本项目后端接口

| 路径 | 方法 | 用途 |
| --- | --- | --- |
| `/api/state` | GET | 读取共享原型状态、revision 和更新时间。 |
| `/api/state` | PUT | 提交 `{ state, baseRevision }` 保存状态；版本冲突返回 409 和最新状态。 |
| `/api/vendor` | GET | 查询两家厂商的凭证是否已配置，只返回布尔状态。 |
| `/api/vendor` | POST | 提交 `{ providerId: "qcc"或"tyc", keyword, parameters, config }`，由服务端调用固定厂商接口；成功返回 `record`、`vendorResponse`、`providerId`、`collectedAt`。 |
| `/api/v1/enterprises/search` | POST | Bearer 鉴权；按地区 / 行业 / 资质 / 规模 / 产业链节点等条件 AND 筛选，返回总数和分页企业列表。 |
| `/api/v1/enterprises/query?keyword=...` | GET | Bearer 鉴权；按信用代码或全称完全匹配，返回单家企业工商详细信息。 |
| `/api/v1/services/{id}` | POST / GET | Bearer 鉴权；按服务 ID 读取配置并分发。`kind=search` 接收 POST 筛选请求，`kind=query` 接收 GET `keyword` 查询；须先在控制台发布服务。 |

`/api/vendor` 只允许上述两家固定只读接口，查询关键字不超过 200 字符，请求体不超过 8 KB，超时为 12 秒；区分未配置凭证、未查到、厂商限流、业务错误和网络超时。演示模式读取 `public/prototype/fixtures/` 的快照，不调用厂商付费接口。

### 对外 API 部署与鉴权

完整后端部署需在 Worker Secrets / 服务端绑定中设置 `ENTERPRISE_API_KEY`，调用方携带 `Authorization: Bearer <API_KEY>`。未配置密钥返回 503，缺失或错误密钥返回 401；接口草稿 / 停用返回 403，精准查询未匹配返回 404。接口配置保存后变为草稿，需在控制台发布后才开放调用。页面不展示或保存真实密钥。

控制台通过「新增API服务」保存 `name`、`id`、`kind`、`version`、`description`。服务 ID 按唯一 URL slug 校验，不能与已有服务重复；同一种 `kind` 可创建多个不同 ID 的接口。新服务默认草稿，其动态路径为 `/api/v1/services/{id}`。动态路由支持 GET / POST 分发，实际允许的方法由服务类型决定；`search` 使用 POST，`query` 使用 GET。原有两条 `/api/v1/enterprises/*` 路径继续保留，服务目录中的新旧接口均支持发布、停用、文档和调试。

批量接口请求体为 JSON 对象，支持 `regionProvince`、`regionCity`、`regionDistrict`、`industry`、`qualifications`、`scale`、`chainNodes`、`keyword`，以及整数 `page`（默认 1）、`pageSize`（默认 20，最大 100）；字符串最长 200 字符，请求体最大 16 KB。不支持的参数会报错。精准接口仅接收一个 `keyword` 查询参数，不做模糊检索。

两类服务统一返回 `{ requestId, code, message, data }`。批量结果 `data` 包含 `count`、`page`、`pageSize`、`records`；精准结果包含 `count`、`record`。企业结果只包含中心 ID、15 个公开标准字段及数据更新时间，不暴露原始来源载荷、内部血缘或配置。接口仅查询已入库数据，不触发厂商付费查询。控制台在线调试复用同一套筛选和参数校验逻辑，持久化最近 100 条浏览器调试记录；API 列表的「最近调用次数」按已保留记录统计近 24 小时成功及失败的已执行调用，点击次数打开该接口明细，可切换近 24 小时与全部保留记录。明细包含时间、调用时服务名与版本、请求 ID、状态码、业务码、返回企业数和执行方式，独立的「最近调试调用」模块已移除。真实外部请求不会覆盖共享状态，也不计入本原型调用统计，生产请求审计需另接服务端日志系统。

### 下游服务新增方式

导航「标准 API 服务」更名为「下游服务」，包含「标准 API 服务」「动态 SQL 查询」「批量订阅推送」三个页签；既有 API 接口和调用明细继续可用。

- **FTP 接入**：只保存演示配置，不接收密码；文件列表为明确标注的虚构远端目录，不发送网络请求。支持 JSON / UTF-8 CSV 结构的样例预览、字段映射及已发布脚本转换；使用同一批处理引擎写入来源候选、企业库和任务，参与信源排序。全量不按缺失行删除，增量采用来源时间及成功检查点；修复失败映射后可重试。更新配置统一在更新任务中维护，正式轮询需后续服务端执行。
- **动态 SQL 查询**：新增、编辑、保存草稿、发布/停用、输入 SQL 和 JSON 命名参数执行，查看结果和最近 50 条执行记录。查询表固定为 `enterprises`，仅暴露公开标准字段，支持 `SELECT`、`WHERE` 的 `=` / `LIKE` / `IN` 和 `AND`、单字段 `ORDER BY`、`LIMIT 1–500`（默认 100）；不支持写入、JOIN、聚合、OR、注释及多语句。参数作为值绑定，不拼接 SQL。修改配置后回到草稿，需重新发布。查询当前企业库，不连接实际数据库。
- **批量订阅推送**：按国民经济行业、注册地区、荣誉资质配置条件，支持预览匹配、发布/暂停、全量或增量、Webhook 地址及频率、模拟投递和明细。一个维度的多值取 OR，维度间取 AND；未选条件表示不限。行业使用当前演示库已有文本，不将样例行业包装成官方完整行业编码字典。增量以成功模拟投递的快照识别变化，失败不推进基线，可重试；首次建立全量基线。Webhook 为 HTTPS 配置，当前流程不发送真实网络请求，定时和真实重试需服务端实现。

## 5. 全量与增量更新语义

**全量更新**刷新当前企业库中的企业，或处理列表 / 系统接口配置返回的数据。真实逐企模式从企业库取请求上下文；单次模式请求配置的接口；演示模式处理所选快照或自定义演示 JSON。这里的“全量”不表示取得厂商全国企业目录，也不会因为本批次缺失某家企业就删除已有记录。

**增量更新**处理接口返回的新增 / 变化记录或指定变更窗口。核心引擎支持 `(windowStart, windowEnd]`：排除起点本身，包含终点；界面可填写起点，留空时采用该来源最近成功检查点。没有厂商变更流时，真实逐企模式仍请求已有企业，以返回记录进行差异处理；可用 `{{updatedAfter}}` 配置增量入参，但不推断已经取得厂商全国增量流。

来源时间缺失时会标记为推定采集时间，不将其当作可信的厂商变更时间；推定时间记录不会覆盖已有明确来源时间的记录。成功检查点只在本批无失败时推进，且不倒退。任务同时保存来源新增 / 更新 / 未变数量、中心企业新增 / 变化数量和失败原因，避免把来源变化误认为企业总量增长。

更新策略统一在「更新任务 → 任务配置」管理，「任务执行」独立展示执行记录并支持选择任务运行；手动运行完成后自动切换到任务执行页签。API 接入页和 FTP 连接页不再配置策略。支持新增、编辑任务，选择更新来源（API / FTP）、全量或增量、更新频率及执行时间。每日/每周按北京时间（UTC+8）执行点计算，每周另选执行日；按小时间隔从上次执行起推进，执行时间字段不用于此频率。支持暂停、启用和立即运行；暂停任务不可执行。本地固定模板文件由用户上传，不参与定时拉取。

原信源策略只迁移一次到 `state.updateJobs`，保留配置与检查点。任务定义与 `state.tasks` 运行日志分开；同一来源可创建多个任务，各自维护检查点。更换来源或全增量方式会重置该任务基线，修改名称和执行频率保留基线。完整成功才推进检查点，部分失败不推进；空批不会将检查点推进到执行时间。连接/校验前置失败也保留记录并计算下一次执行，避免无记录反复执行。

原型每 30 秒检查一次到期的演示 API / FTP 任务，仅页面打开时运行。真实厂商接口不会被演示定时器自动调用；关闭页面后不运行。FTP 任务按自身检查点读取符合规则的演示文件，完整成功才登记文件版本；不受其他任务的文件去重记录阻挡。生产部署需要服务端调度、传输、重试、凭证额度及运行锁。

## 6. 文件导入

支持 UTF-8 CSV 和常见 `.xlsx` 文件的首个工作表；单文件不超过 20 MB、最多 5 万行，仍受整份原型状态 5 MB 上限限制。按模板填充数据，表头不得缺失或重复，文件先检查预览，再确认入库。

本地上传使用 6 列固定模板：企业全称、统一社会信用代码、企业资质、企业规模、产业链节点、数据更新时间。企业全称与统一社会信用代码必填，其余列的值可空；系统按统一社会信用代码关联并更新企业来源记录。资质和产业链节点支持中文 / 英文分号、逗号拆分并去重。此流程不提供文件字段映射，也不需要选择、测试或发布加工脚本；请直接按模板填写，不使用自定义列名。浏览器不支持当前 XLSX 解压方式时，可另存为 UTF-8 CSV。

「本地文件上传」页签展示每次上传记录，包含信源名称、文件名 / 下载链接、上传时间、行数与处理结果。原件以 Blob 保存在当前浏览器的 IndexedDB，下载时生成临时文件链接；不是服务端永久 URL。完整后端部署只共享记录元数据，不上传原件到 D1，因此另一浏览器 / 设备可能看得到记录但无法下载原件。清除浏览器站点数据会删除本机原件；原型未实现集中对象存储。

## 7. 完整后端的持久化与原型边界

- 数据存储：D1 的 `prototype_state` 表中保存一份共享工作空间状态，包含来源配置、映射、脚本、来源记录、企业库、任务与服务调用。
- 并发保存：客户端携带 `baseRevision`，服务端原子比较并递增 revision；冲突返回最新状态，避免静默覆盖其他窗口的保存。
- 可恢复性：普通刷新会重新从服务端加载；不会用浏览器临时状态替代服务端保存成功。共享存储不可用时展示明确错误。
- 容量：单份状态 JSON 不超过 5 MB。当前采用整体快照保存，适合原型评审；规模化使用需要拆分实体表、分页、任务队列和历史版本存储。
- 工作空间：当前所有有权访问本原型的用户共享同一份演示状态，尚未实现应用内多租户、细粒度角色权限或独立数据集。
- 部署访问控制：原有企业 API 与新增动态服务路由均使用基于 `ENTERPRISE_API_KEY` 的 Bearer 鉴权；控制台状态写入、厂商代理仍依赖托管环境访问边界。若公开部署完整 Worker，需保护控制台和管理路由，并增加角色权限、租户级授权及限流后再配置付费厂商凭证。GitHub Pages 公开版没有部署服务端路由。
- 查询：企业筛选和单企精准查询使用已入库数据；精准查询不会在后台自动发起新的厂商付费查询。未找到时需要先通过接入任务补齐企业。
- 历史：保留当前来源候选、处理任务、上传记录及浏览器调试记录，不是完整的历史快照仓库；本版本不实现删除同步、集中上传原件存储或后台无人值守调度。

## 8. 本地运行、检查与构建

### 环境与安装

需要 Node.js `>=22.13.0`，支持 Windows、macOS、Linux。首次在独立源码目录安装依赖：

```sh
npm run install:ci
```

该命令按锁文件执行安装；已有正常依赖时无需反复安装，不要同时启动多个安装进程。

### 初始化 D1 并预览

在项目根目录执行：

```sh
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_sparkling_harrier.sql
npm run dev -- --hostname 127.0.0.1 --port 4317
```

打开服务器实际输出的地址，并访问 `/prototype/index.html`。本例使用 `http://127.0.0.1:4317/prototype/index.html`；不指定端口时 portable 开发模式默认从 5173 启动。迁移只需对新的本地数据库执行一次；已有 `prototype_state` 表时不要重复执行建表 SQL。

开发和构建预览共享 `.wrangler/state` 下的本地 D1 状态。缺少 DB 绑定或未迁移时，界面会显示共享存储 / 数据表未就绪信息。

### 功能检查与构建预览

```sh
node --test tests/*.test.mjs
npm run build
npm start -- --port 4318
```

`npm start` 使用构建生成的 Worker 配置在本地预览，不会执行发布。以服务器实际输出的 URL 为准。

项目保留 Vinext、Cloudflare Worker、D1 和 Drizzle 基础结构；修改数据库结构后可运行 `npm run db:generate` 生成迁移。无需另建 `wrangler.jsonc`。
